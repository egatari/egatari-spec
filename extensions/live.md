# Egatari extension `live` — Draft v1

**Status:** draft, 2026-10-21. Registered in [../extensions.md](../extensions.md). Consumed by **players**: a player that implements it lets the learner take part in a live room (questions, polls) from the distributed lesson itself, without scanning a code or opening another app. Players that ignore it render and time the lesson exactly the same; nothing in this extension is part of the stage, so *(i, k, t)* rendering, video and print are unaffected.

This is the only part of Egatari that lets a lesson connect to the network. It is opt-in by the author, limited to one declared endpoint and to a time window, and visible to the learner while connected.

## 1. Data (`extensions.live`)

```json
{
  "v": 1,
  "endpoint": "https://live.egatari.org",
  "room": "r-7k2q6xw4",
  "key": "base64url capability, 22+ characters",
  "window": {"from": "2026-10-30T09:00:00+09:00", "to": "2026-10-30T11:00:00+09:00"},
  "activities": {
    "*": [{"id": "qa", "kind": "qa"}],
    "s-k3f9q2:2": [{"id": "p1", "kind": "poll", "label": "4 枚目「更新の式」・ステップ 2", "prompt": "学習率を大きくすると？", "choices": ["速く収束", "発散しうる", "変わらない"]}]
  }
}
```

| Member | Meaning |
|---|---|
| `endpoint` | the only origin the player may connect to. MUST be `https:`; a player MAY accept a loopback `http:` origin (`127.0.0.1`, `localhost`) only in a development build, never in the player that producers embed in distributed lessons. |
| `room`, `key` | the room (`r-` and 8 lowercase base32 characters) and a capability to join it. The key travels in the WebSocket address when joining; it is already in the file, so this exposes nothing new. Anyone holding the file can join while the room is open (see §4). |
| `sourceSha256` | written by the producer into an exported derivative only (play-only derivatives carry no index): the lesson's source hash, sent with questions so that they map onto this version of the lesson. A lesson's own settings MUST NOT carry it. |
| `window` | the only interval in which the player may connect. Outside it the player MUST NOT make any request. Players MAY allow a small clock skew at both ends (at most 5 minutes; the reference player uses 2). |
| `activities` | step key (or `"*"` for the whole lesson) → list. `kind`: `qa` (questions: participants send questions from any step; each question carries the step key on screen and, if the participant circled something, a region in stage coordinates (strokes as in the review-notes shape of Egatari Studio), and the lesson's `sourceSha256`, so that questions can be mapped onto the lesson; the host sees them, may group similar ones and may send a short reply (at most 200 characters; a new reply replaces the old), shown to the asker and, if the host chooses, to everyone together with the question it answers; the others in the group get it privately. Regions are never attached to `"*"` without a step on screen), `confused` (a one-tap "I don't follow" at the current step, without text; a toggle the participant can take back, at most one per participant and step; counted per step; a join page without a step on screen uses `"*"`), `poll` (single choice; `choices` required; a vote is the 0-based index of the choice; v1 shows learners no tally). `board` (short notes on a shared board) is reserved for v2. Each activity MAY carry `label` (at most 80 characters): where it is, in words people recognize (e.g. "Slide 4 «The XML wall» · step 1", or "Conclusion"), which the teacher's page, the join page and the results show instead of the step key; producers SHOULD generate it from the slide number, title and step. |

In a play-only derivative (which has no index, spec §3.7) players read this object from the runtime block `deck-extensions` (`{"live": {...}}`, spec §3).

Authoring: activities are set in the editor when exporting a play-only derivative "with a live room"; v1 defines no `narration.md` lines. The room must know the same `activities` (to label results and to reject votes for unknown activities or choices): in v1 the editor shows them for the teacher to give to the room's page together with `room`, so the editor itself still makes no request. The author's own lesson keeps `extensions.live` without `key` (the key is added to the exported derivative only).

## 2. Player behaviour

A player that implements `live`:

1. MUST NOT open any connection unless `extensions.live` is present, the current time is inside `window`, and the lesson is the top-level document. Inside any frame (an editor preview, an LMS, an embedding host, Player P8, §10.1) it never connects, whether or not the host would allow it; it MAY show the room's address (the endpoint and the room id) instead. Video mode, print and the presenter's view never connect either.
2. MUST, before or at the first connection, show that the lesson connects to `endpoint` (e.g. "This lesson is connected to a live room at live.egatari.org"), and while connected show a persistent indicator with a way to disconnect. The learner MUST tap once ("Join") before the first connection of a session; joining must not require an account. (Connecting without a tap was considered and left out of v1: lessons for minors.)
3. MUST send only what an activity needs: the learner's question or choice, the activity id and step key, and a random participant id generated on the device (no name unless the learner types one). For `qa` under `"*"`, the step key is the step on screen when the learner sends the question; it is attached only to what the learner chose to send. It MUST NOT send viewing position, timing, playback events or any other telemetry.
4. MUST restrict its connections to `endpoint` and MUST NOT load scripts, styles or images from it; activity content arrives as data and is shown as text. The file's policy (spec §4.2) adds to `connect-src` the endpoint for both schemes (e.g. `https://live.egatari.org wss://live.egatari.org`, since some browsers do not apply an `https:` source to `wss:`) and nothing else; players SHOULD also check every connection against `endpoint` themselves. The policy need not allow `unsafe-eval`; components from withdrawn releases that need it then show their fallback (spec §6).
5. Shows activities outside the stage (a pane, spec §1.0), so that the stage, captions and marks stay as authored, with one exception: a component bound to a `poll` (it names the activity id, e.g. `poll="p1"`, spec §8.4 "Viewer input") MAY show that poll's aggregated counts on the stage. The player passes the counts to the component only after the teacher has chosen to reveal the results, only as counts per choice (never who chose what), and not at all while fewer than 3 participants have answered; counts never appear in video, print or exports of the lesson. A `poll` for a step is shown while that step is on screen; `qa` is available for the whole window. Text from the service is shown as text (never as markup).
6. Reconnects only after a close that the service marks as retryable, with increasing delays, and only inside `window`; it stops trying when the window ends. In the reference protocol (egatari/live PROTOCOL.md) the retryable closes are 4423 room closed (wait at least 30 s; the teacher may reopen), 4425 too early (wait until `window.from`), 4429 too many requests and 4430 room full (wait at least 60 s); every other close, including 4441 (the teacher declined this learner), is final. A learner waiting for the teacher's approval stays connected and is told so; that is not a close.

## 2A. A host acting for the lesson

A host (spec §10.1) that plays a lesson in a sandboxed frame — where the lesson itself never connects (§2.1) — MAY implement `live` on the lesson's behalf: for example a player page where a viewer opens a lesson file from the device (on systems whose browsers cannot run a local HTML file, such as iPhone and iPad), the file being read in the page and never uploaded. Such a host:

1. reads `extensions.live` (from the index, or from `deck-extensions` in a play-only derivative) with a parser that runs nothing (spec §11), and keeps the lesson's frame without network access as §10.1 requires;
2. follows §2 itself: the window, the one-tap join, the visible indicator, the data rules (§2.3), the endpoint restriction for its own connections, the retry rules;
3. learns the current step from the embedding events ([Egatari Player 1.0](../egatari-player-1.0.md) P8, `position`) to show a step's poll, and shows activities outside the lesson's frame;
4. serves the page from an origin separate from any editor, so that lessons played there cannot reach an editor's storage.
5. MAY connect only to endpoints it knows (an allow-list, e.g. its own reference service) and offer the join page (§4) for any other endpoint, so that a lesson cannot make the host a client of an arbitrary server;
6. MAY hide the lesson's own live indicator and pane inside the frame (where the lesson cannot connect), so that the viewer sees one way to join, the host's.

## 3. Results

Results belong to the teacher. The room service lets the teacher download them as JSON (`{room, window, activities, responses}`; the shape of `responses` is defined by the reference protocol, [egatari/live PROTOCOL.md](https://github.com/egatari/live/blob/main/PROTOCOL.md)), which the editor MAY add to the teacher's lesson as an attachment with role `data` (spec §3.8). Results are never written into play-only derivatives. Readers of results (editors importing them) MUST ignore members and activity kinds they do not know, and SHOULD say what they skipped, so that a newer room service never makes an older editor refuse a teacher's results; the room service MUST NOT record activities the teacher did not declare (it does not infer one, e.g. `confused`, for a room that declared none). Transitional: a room created before its activities were given to it (the earlier two-step setup), whose activities are absent rather than declared empty (`{}`), MAY keep accepting `qa` and `poll` responses as before; it still never gains an activity kind the teacher did not choose (no `confused`). Rooms created by one-way setup always declare their activities.

## 4. Room service (informative)

The reference service at `live.egatari.org` (Egatari Studio) keeps rooms only for their window plus a short grace period and then deletes them. The editor makes no network requests. Either the host creates a room on the service's page and copies `room` and `key` into the editor, or (preferred, one way only) the editor generates them itself and gives the host one string with them and the activities (`activities` required; `{}` accepts nothing); the host pastes that string once on the service's page, passes its bot check, and the service creates the room with exactly that `room`, `key` and activities, refusing a `room` that already exists and never changing or handing over an existing room. Because `room` and `key` travel in every exported lesson, holding the file MUST NOT be enough to create the room (a learner who received the file early could otherwise create it first and become its host): a service offering one-way creation MUST require proof of a secret that no lesson carries. In the reference service the editor draws a random **setup secret** (32 bytes) and derives `room` and `key` from it by SHA-256 under separate labels; the string carries the secret, the service derives `room` and `key` again and compares them, and does not store the secret (string format and test vector: PROTOCOL.md §2.1). After a room has expired and been deleted, the holder of the secret may create it again with the same string; the window cannot be changed after creation. Editors keep the secret and the key out of the author's own lesson and out of storage they do not control; they SHOULD let the host save the string as a secret of their own, like the teacher key. Managing a room needs a separate **teacher key**, shown once when the room is created and kept in the fragment (`#…`) of the teacher's page address; it is never written into a lesson or an export. The teacher can open and close a room, require approval before learners appear, and replace the key (which locks out copies of the file that leaked). Learners' questions are visible to the teacher only unless the teacher shows them. For learners whose device or context cannot connect from the lesson (a frame, a file viewer that runs no scripts), the service offers a join page (`/join`) that takes the room and key from a link the teacher shares, in the fragment (`#room=…&key=…`, never sent to the server as part of the address), and speaks the same protocol with the same data rules as §2.3. Because a join page has no lesson file, it asks the room for the activities the teacher gave it (in the reference protocol, `{t:"activities"}`, answered only to admitted learners and sent again when the teacher changes them) and shows every poll in declared order, each labelled with its step (`"*"`: the whole lesson); the teacher says aloud which one to answer. Players inside a lesson file read activities from the file (§1) and do not need this request.

## 5. Open questions

- Whether `board` (v2) and a teacher overview of learners' work need end-to-end encryption by default, and how that interacts with moderation.
- Whether a lesson may declare more than one room (several classes, one file) or the editor exports one derivative per room.
- Minimum notice wording in both languages.
- Accounts (owner's decision, 2026-10-21, informative for the reference service): v1 rooms (text questions and polls, about 40 participants, up to about 2 hours) need no account; room creation is protected by a bot check (e.g. Cloudflare Turnstile) and per-client limits. Larger or longer rooms need a light sign-in (an e-mail link or a common identity provider) with a monthly free allowance. v2 activities that accept images or shared drawings (`board`, photos of learners' work) require a signed-in teacher, so that someone is accountable for what a room holds. Whether a signed lesson (`signatures-v1`) can stand in for a sign-in is open.
